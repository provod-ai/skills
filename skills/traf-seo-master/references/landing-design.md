# Landing quality and browser verification

Use for a website or landing page that supports an acquisition bet: clearer value, useful interactive results, stronger evidence, readable presentation and a complete conversion journey. This route includes web motion and needed graphics. It does not reopen the project's excluded short-video production scope. Sources checked 2026-11-01; no design MCP, asset generation or browser implementation was activated during this research.

## Inputs and reference access

Start with the real product URL/source checkout, actual locale, reader/search intent, offer, desired next action, current brand assets/tokens, evidence of product behavior, and available host tools. Inspect the existing implementation before selecting a framework or replacing components. Preserve the brand and established user journey; missing facts remain questions or draft markers, never invented testimonials, customers or product screenshots.

## Smallest useful landing change

1. **Name the visitor's task.** Write the query-to-page-to-result path. A calculator should produce the promised calculation; a comparison should expose real criteria and caveats; a product page should lead to the actual service. Define the arrival cohort and primary organic-visit measure. CTA clicks, activation and purchases diagnose journey quality without replacing the owner's visit target.
2. **Audit the current page.** Inspect headings, first-screen answer, proof, navigation, link destinations, forms, loading/empty/error/success states, mobile overflow and next-step friction. Capture the existing browser state before editing so the improvement is reviewable.
3. **Use available design guidance.** Discover the current host's installed skills and read the relevant one. `impeccable`, frontend/design-taste skills may help when actually exposed. The public [Impeccable source](https://github.com/pbakaus/impeccable) offers existing critique, polish, accessibility and motion guidance; local and upstream versions can differ. Do not auto-update, install hooks, assume cross-host availability or claim its detector ran merely because a skill is listed.
4. **Implement one coherent page improvement.** Reuse existing components/tokens. Explain the offer clearly, connect evidence to the promise, and make the next action obvious. Add real product captures, diagrams or permitted graphics where they explain something copy cannot. Keep real text in HTML; do not bake essential headings or CTAs into an image. Asset generation is conditional on an available capability and its established provider/account/spend authority; use supplied assets or an honest placeholder in a draft when absent.
5. **Make it usable under constraints.** Check semantic structure, keyboard access, visible focus, form labels, contrast, zoom and responsive behavior against [WCAG 2.2](https://www.w3.org/WAI/WCAG22/quickref/). Use motion to communicate state or sequence. Provide a reduced-motion alternative, keep core content visible without animations, and allow disabling nonessential interaction motion; [W3C's explanation](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html) describes the user need.

## Evidence before completion

Every visible UI/HTML change requires real browser QA: navigate the changed page, save and inspect screenshots, and read console errors. Use the host's available Playwright browser tools; [upstream Playwright](https://github.com/microsoft/playwright) is the ready fallback only when its runtime is actually available. Exercise desktop/mobile, keyboard, reduced motion, and the intended result/CTA path. A static mockup or source read is insufficient. Automated [axe-core](https://github.com/dequelabs/axe-core) findings can supplement manual checks, not establish complete accessibility.

Measure loading and layout shifts with the existing Lighthouse/DevTools path. Preserve raw reports, viewport, build and runtime errors. Distinguish lab results from real-user LCP/INP/CLS: [Web Vitals guidance](https://web.dev/articles/vitals) explicitly separates lab and field measurement. A high score does not prove rankings or visits.

Deliver the editable page changes, asset provenance, before/after browser evidence, checked states, defects and exact missing dependencies. If no browser can run, report visual verification as blocked rather than complete. Publishing requires its own actual authority and readback. Continue acquisition measurement by cohort after release; a polished page or public gallery resemblance alone does not prove reach.
