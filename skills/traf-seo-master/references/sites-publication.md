# Useful sites, programmatic pages and publication

Inspect the actual project's renderer/CMS/Git publisher, site/tenant/locale identities and production constructor. Reuse the current working path. A new site/template is justified by a real audience, useful operation or data family, not the number of domains/pages an agent can generate. Available AutoSEO/SERPsmith/WordPress/Sanity/static renderers are alternatives to qualify, not a mandatory stacked platform.

For programmatic work define a real entity/task/fact spine: eligibility, unique useful attributes, source revisions and supported capabilities. Materialize only valid combinations. Keep canonical intent/brand/site/locale/asset identity, URL history, translation family, source facts and a deterministic link graph. Reject missing/unsupported inventory and factual claims; don't replace them with generic SaaS promises. A valid page schema or escaped HTML proves structure, not truth or acquisition.

## Candidate and operation contract

Freeze coherent content/template/config/schema/locale/evidence bytes and actual target identities before a write. Include previous remote revision, allowed diff, authority reference, source checks, build/render checks and rollback candidate. Drift invalidates that candidate; don't mix source/config revisions or overwrite owner WIP.

Persist publication intent and operation key before submission. Retain attempt state, redacted request hash, provider task/object/deploy ID, response, raw reference and public readback. Use documented idempotency if supported. A slug, queue lease or successful job ID alone does not prevent duplicate remote creates. Unknown outcome after a possible write stays UNKNOWN and reconciles by authoritative receipt/object/revision before resubmission. Timeout does not prove cancellation.

Read back public/rendered content, metadata, canonical/hreflang/sitemap and primary user action. CMS200, Git push, deploy success and search notification are intermediate. Rollback is a distinct operation with target drift checks and readback, not a blind restore that erases another author's edits or receipts.

The first real vertical is one qualified useful asset through the actual publisher and normal user path. Working publication admits the acquisition experiment; repeatable traffic must still be measured before expanding the family. Newly visible UI requires browser screenshot/console/interaction checks, including relevant mobile and accessibility states, using actual host tooling. If unavailable, preserve the specific unverified check.

Ready source examples: [AutoSEO](https://github.com/codextde/autoseo), [SERPsmith](https://github.com/emiliojohann/SERPsmith), [pseo-ai-kit](https://github.com/swarmclawai/pseo-ai-kit), [WordPress REST posts](https://developer.wordpress.org/rest-api/reference/posts/), [official WordPress MCP adapter](https://github.com/WordPress/mcp-adapter). Their integration seams, paid/provider requirements and native harness support need a bounded current canary. No connector or production authority is created by listing them.

Output: complete reviewed asset/candidate, target-qualified publisher action/readback where authorized, current operation state, remaining index/acquisition evidence and update/rollback references. No broad site/network deployment or external messages are inferred from package installation.

## Choose the page family

Record family, real source data, eligible entities, refresh path, useful result and intended conversion before generation.

| Family | Required useful result |
| --- | --- |
| Templates | Editable or downloadable material that works in the advertised format |
| Curated selections | Dated criteria and sourced evaluations |
| Converters | Correct operation, units, data freshness and usable output |
| Comparisons | Verifiable differences and use-case-based recommendation |
| Examples | Real examples with organization, context and explanation |
| Locations | Real service/location facts and useful local differences |
| Audience pages | Distinct tasks, relevant features and audience evidence |
| Integrations | Current setup, real prerequisites and checked examples |
| Glossary | Accurate definition, context, examples and related concepts |
| Translations | Localized main content, local facts and tested locale relationships |
| Directories | Qualified records, useful selection/filtering and refresh path |
| Entity profiles | Sourced identity/attributes and useful original synthesis |

Evaluate the requested family against demand and product supply. Check whether the existing renderer/CMS supports the real item count and plan, incremental data refresh, initial useful HTML, conditional sections, per-page metadata/index controls and publication cost. Compare justified alternatives using those constraints. Prove a small qualified publish/update/remove path and measure capture and maintenance before scaling.
