# Strategy, briefs and useful original content

Select a qualified opportunity from acquisition/intelligence work, not merely a large keyword. Identify user task, current search/AI result formats, real product capability, differentiated value and expected route to attention/use. Topic choice needs current demand/competition/distribution evidence; if unavailable, deliver a qualified research brief instead of inventing a winner.

Build the source/fact pack first: what is observed, source/date/scope, exact product/entity version, supported assertions, unresolved questions and the useful original result. Prefer own reproducible tests, data, runnable examples, editable templates or a real operation when these solve the intent. Do not claim a test, testimonial, benchmark, price or feature that was not obtained. A structural validator cannot certify truth.

The technical/editorial brief includes primary intent and exact query provenance, target audience/market, page type, current comparator strengths/gaps, original contribution, factual sources, executable/editable example, content hierarchy, necessary diagrams/assets, internal-link plan, relevant CTA and measurement. It also states what will make the page different enough to deserve attention, how it will be distributed/discovered, update obligations and acquisition success/futility criteria. Word count and keyword repetitions are diagnostics, not a strategy.

Draft the complete requested artifact using the selected strong host model and existing workflow. Keep facts/units/versions intact, make explanations concrete, and review factual uncertainty separately from voice/style. For natural editing/statistics, load content-quality.md. Keep titles/metadata honest and useful; avoid mass name-swapped pages or arbitrary date refreshes.

Before publishing, a reader should be able to perform the intended task or make the intended decision. Verify examples against the real documented/current behavior within existing account/call authority. Keep missing integration/runtime evidence explicit. A local code example that has not run is not a tested recipe. Preserve source version and affected derivatives so factual changes update more than the display date.

Use suitable ready components selectively: [Marketing Skills](https://github.com/coreyhaines31/marketingskills), [SEO Machine](https://github.com/TheCraigHewitt/seomachine), [GPT Researcher](https://github.com/assafelovic/gpt-researcher) or available hosted research/CMS workflows. These have different runtime/provider/model requirements; their defaults and marketing acquisition claims are not inherited authority. Never silently activate paid APIs or weaker model defaults.

Deliver the brief and finished draft/tool/template requested, source/claim ledger, testing limits, planned publication/attention path and refresh triggers. For each significant edit, a short fact-change summary should reveal additions/removals or weakened certainty. Use the actual publishing module for external effects, not a text-generation success flag. Guidance: [Google useful content](https://developers.google.com/search/docs/fundamentals/creating-helpful-content), [generative-AI content guidance](https://developers.google.com/search/docs/fundamentals/using-gen-ai-content).
